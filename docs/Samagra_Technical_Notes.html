1The big picture

Every web app runs on two computers. Knowing which job happens where explains most design decisions in Samagra.

Client side: the browser

The user's laptop or phone. It runs HTML, CSS and JavaScript.

  • Shows pages and forms
  • Reacts to clicks: tabs, popups, drag-and-drop
  • Draws the dashboard charts
  • Sees only what the server sends it

Server side: Samagra itself

Your laptop today, a VW server later. It runs the Python code.

  • Checks who is logged in and what they may see
  • Reads documents, compares quotes, counts TAT
  • Talks to the AI, email and price search
  • Holds the database and the secret keys
Rule of thumb: anything that must be trusted (prices, permissions, the "same product" check, API keys) happens on the server. The browser only displays results, so a user cannot tamper with them.

How one request travels

Browser:  "open /queue/57"
   │
   ▼
Uvicorn        listens on port 8000, receives the request
   │
   ▼
FastAPI        finds the function for /queue/57
   │
   ▼
deps.py        is someone logged in? are they a buyer?  ── no ──▶ login page or 403
   │ yes
   ▼
buyer_routes.py   the page's own function runs
   │
   ├──▶ db.py                     reads the case from sourceflow.db
   ├──▶ tat.py, advisor.py …      works out TAT, next action, alerts
   │
   ▼
Jinja2         fills templates/buyer/queue_detail.html with the data
   │
   ▼
Browser        receives a finished page, styled by CSS, made interactive by JS

2The tech stack, tool by tool

For each tool: what it is, what it does in Samagra, and why it was chosen over the alternatives.

2.1 Server

ToolWhat it does in Samagra
Python 3.14The language of all server code: routes, database, AI calls, document reading, maths, email.Why: the strongest ecosystem for AI and for reading PDF, Word and Excel. Java or Node.js are weaker at both.
FastAPIThe web framework. It maps each web address to a Python function (about 60 routes in routers/), checks access before every page, reads and validates form fields and uploaded files, and waits on slow AI calls without blocking other users (async).Why not Django: too heavy, with a built-in admin and database layer we did not need. Why not Flask: it would work, but has no built-in access checks, form validation or async. History: Samagra began on Streamlit; the challenge owner disliked its UI, so the pages were rebuilt on FastAPI and the business logic was kept.
UvicornThe server program. It listens on port 8000 and hands every browser request to FastAPI. run.ps1 starts it.Why: FastAPI defines what to answer but cannot listen on a network port by itself. Uvicorn is its standard partner. In production it would run as several workers behind nginx.
Starlette sessions + itsdangerousLogin sessions. After sign-in the browser gets a cookie holding only the user's email, signed with a secret key. The role is re-derived from the email on every request.Why: if anyone edits the cookie, the signature breaks and the server rejects it. No session database needed.
python-multipartReads form submissions that contain files: carts, SFOs, quotes, InfoSec documents, supplier replies.Why: FastAPI uses it underneath to receive uploads.
httpxMakes calls to outside services: the AI (LLMaaS or Ollama), Microsoft Graph for email, SerpAPI for prices.Why: modern, supports timeouts and custom certificates.
numpyCounts working days for TAT (busday_count, which skips weekends).Why: one well-tested call instead of hand-written date loops.
truststoreUses the Windows certificate store for secure connections.Why: the VW VPN re-signs HTTPS traffic with a VW certificate that Windows trusts and Python does not. Without this, price search fails on the VPN.
msalMicrosoft's sign-in library. Does the one-time sign-in for the mailbox, then refreshes access silently.Why: Microsoft's official library for Graph access.

Server-built pages mean one language, no build step, and fast first loads. Where interactivity is needed, a little plain JavaScript covers it.

2.4 Outside services

ServiceWhat it does in Samagra
VW LLMaaS (gpt-4o)The best-quality AI. Needs the VPN and the team's credentials, which are read from environment variables and never written in code.
Ollama (qwen7b)The same job on your laptop, free and offline. The LLM_MODE setting picks llmaas or ollama; the code is the same for both.
Microsoft GraphSends every email and reads the intake inbox, as procurement.intake.demo@outlook.com.Why not SMTP: the VW network blocks it. Graph runs over normal HTTPS. The SMTP code is still present but unused.
SerpAPISearches Google Shopping India (twice) and Amazon.in (once) per item for the market price check. Free plan: 250 searches a month.
Cloudflare TunnelGives your laptop a public web address, so suppliers anywhere can open their private link. Started by run.ps1 -Tunnel; the address changes on every restart.
Git + GitHubVersion history; the code lives in a private repository.

2.5 What the AI does, and what it never does

The AI reads: quotations in any layout, carts the table reader cannot parse, emailed requests, whether a quote covers what was asked, and whether an online listing is a similar product. It also drafts the supplier note and answers "Ask this case".

The code decides: tax stripping, currency conversion, ranking, TAT, buyer allocation, next action, "same product" by model number. Every figure the AI reports is checked against the source document before it is shown.

Say it this way: "The model reads, the code decides, and a person makes every decision."

3The database

One file, sourceflow.db, using SQLite. Samagra created 15 tables. SQLite adds one more of its own, sqlite_sequence, which only stores the next ID number, so the file holds 16.

users                        who can log in

cases                        one row per sourcing request (63 columns)
 ├── attachments             every document on the case
 ├── line_items              shopping-cart lines read from the cart
 └── audit_trail             every action: submitted, checked, enquired, approved…

rfq_rounds                   supplier enquiries (may link to a case)
 ├── rfq_documents           files sent to suppliers
 └── rfq_invitations         one per supplier: private link, status, reply
      └── rfq_response_files what each supplier sent back (v1, v2…)

inbound_emails               requests that arrived by email
 └── inbound_attachments     their files

drafts · password_resets · device_tokens · agent_runs     helpers
TableHolds
casesThe case itself: requester, topic, value, currency and exchange rate, tax basis, status, assigned buyer, TAT dates, PO number, offer analysis, offer comparison, market price check, InfoSec answers.
attachmentsEach uploaded document: type (cart, SFO, RFQ, offer, InfoSec clearance…), filename, where the file is on disk.
line_itemsCart lines: description, quantity, unit, unit price, amount.
audit_trailHistory of the case: who did what and when, marked as visible to the requester or internal to Procurement.
rfq_roundsOne supplier enquiry: reference, subject, note, deadline, status, linked case, InfoSec answers, analysis.
rfq_documentsFiles attached to the enquiry email.
rfq_invitationsOne supplier: email, private token, sent and opened times, accepted or declined, reply text, completeness check.
rfq_response_filesFiles a supplier sent back, with upload time, which is how v1 and v2 are told apart.
inbound_emailsEmails fetched from the intake inbox and their review status.
inbound_attachmentsThe attachments of those emails.
usersName, email, salted password hash.
password_resetsPassword reset tokens, stored hashed.
device_tokens"Remember me" sign-ins.
draftsA new request between form step 1 and the confirm page.
agent_runsA log of every agent run: what it saw, decided and did.

Documents are not stored inside the database. They sit in folders (repository/, rfq_rounds/) and the database stores their location. That keeps the database small and fast.

New columns are added safely at start-up (_ensure_columns in db.py): existing data is never dropped.

Why SQLite: no database server to install, one file, perfect for a prototype. For VW-wide use it would move to Postgres, already on the architecture slide. The SQL is standard, so the move is straightforward.

All in sourceflow/. Grouped by the job they do.

4.1 Core: start-up, settings, rules

main.pyThe front door. Creates the app, sets up signed sessions and the /static folder, plugs in every router, runs the database setup on start, and serves /home and /dashboard, which choose the right page for each role.

4.4 The AI and the comparing

FileWhat it is for
llm.pyThe only file that talks to the AI. Connects to LLMaaS or Ollama and holds every prompt: read offers, confirm items, check scope and RFQ alignment, read cart lines, read quoted products, match online listings.

9Two journeys through the code

A requester submits a new sourcing request

  1. requester/new_request_step1.html shows the form; conditional-fields.js and new-request-upload.js handle show/hide and uploads.
  2. Submit goes to /requests/new in requester_routes.py, after deps.py confirms a requester is signed in.
  3. validators.py checks fields, documents and InfoSec. On an error the form comes back with the message.
  4. parser.py reads the cart's line items (AI fallback, figures verified). tat.py works out the TAT band.
  5. drafts.py and the drafts table hold everything; new_request_step2.html shows the confirm page.
  6. On Submit, the case is created in cases, files move to repository/, rows go into attachments, line_items and audit_trail, and config.py assigns the buyer by commodity.
  7. notifications.py emails the requester through Graph (mailbox.py).

A buyer runs the market price check

  1. The buyer clicks Check online prices; offer-analysis.js shows "Checking prices…".
  2. /queue/57/market-check in buyer_routes.py runs after deps.py confirms a buyer.
  3. benchmark.py reads each quote's product and unit price through llm.py, and checks both appear in the document.
  4. It searches Google Shopping twice and Amazon.in once through SerpAPI (httpx with truststore).
  5. Code keeps only listings naming the exact model, drops accessories, used items, books and import stores, and ignores prices far from the rest.
  6. Prices are put on one basis (₹ including GST) and the gap to the cheapest major retailer is calculated.
  7. db.py saves the result on the case; _market_check.html shows it.

10Quick answers for the jury

What is the stack?
Python with FastAPI and Uvicorn on the server, Jinja2 server-rendered pages with plain JavaScript and Chart.js, SQLite for data, gpt-4o through VW LLMaaS or a local model through Ollama, Microsoft Graph for email, SerpAPI for market prices.
Why FastAPI?
Per-page access control, validated forms and async handling of slow AI calls, without Django's weight. The business logic is framework-independent, which is why moving off Streamlit was quick.
How is access controlled?
Every page declares who may open it, and the check runs before the page's code. Sessions are signed cookies, and the role is re-checked on every request. Suppliers get a random, revocable link to one enquiry only.
How many tables?
Fifteen: four for cases, four for supplier enquiries, two for email intake, three for users and sign-in, two helpers. Documents are stored as files and referenced from the database.
How do you trust the AI?
The model reads, the code decides. Every figure it reports is checked against the source document before it is shown, and a person makes every decision.
Is company data safe?
The AI runs on VW's own LLMaaS or entirely on the local machine. Secrets are environment variables, never in code.
What would production need?
Postgres instead of SQLite, VW single sign-on, SAP integration (carts in, PO numbers out), and hosting on a VW server or container. All four are on the architecture slide as proposed.
